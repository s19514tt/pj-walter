# ピンイン声調 POC

音声 → Gemini → **「聞こえたピンイン（声調付き）」＋「漢字」** の2出力を取り、
**本来あるべき声調**と突き合わせるだけの単体HTML。中国語モードに声調フィードバックを
実装する前に、**そもそもGeminiが声調の間違いを検出できるのか**を確かめるためのもの。

アプリ本体とは独立していて、Flutterのビルドには一切影響しない。

| ファイル | 用途 |
|---|---|
| `autotest.html` | **TTS自動テスト（おすすめ）**。合成音声で50ケースを機械判定。人の発音に依存しない |
| `index.html` | 録音版。自分の声で試す |
| `poc.js` | 共通ロジック（ピンインの音節分割・声調差分・Gemini呼び出し・WAV） |
| `cases.js` | 自動テストの50ケース定義 |

## 動かす

```bash
cd tool/pinyin_poc
python3 -m http.server 8000
# → http://localhost:8000/autotest.html  （TTS自動テスト）
# → http://localhost:8000/index.html     （録音版）
```

`file://` でも開けるが、ブラウザによってはマイクが使えないので `localhost` 経由が確実。

Gemini APIキーは画面上部に貼る。キーは `localStorage`（この端末のこのブラウザ内）に
保存され、送信先は `generativelanguage.googleapis.com` のみ。

## 自動テスト版（autotest.html）

**人の発音に依存せず、ボタン1つで50ケースを機械判定する。**

### 仕掛け

TTSに「崩れた声調」を喋らせるために、対象の漢字を**同音別声調の実在漢字**に置き換える。

```
元の文        我去超市买几个水果。   → … shuǐ guǒ
読ませる文    我去超市买几个睡果。   → … shuì guǒ   ← 綴りは同じ、声調だけ違う
```

`睡` は `shuì` としか読まないので、TTSは普通に読むだけで狙った声調の崩れがそのまま音になる。
あとはその音声をGeminiに投げて、返ってきたピンインの該当音節が `shuì`（実際に鳴った音）か
`shuǐ`（正しい声調）かを見るだけ。**判定は完全に自動**で、人が耳で判断する必要がない。

### 判定

| 結果 | 意味 |
|---|---|
| **検出** | 崩した声調をそのまま報告した ＝ 音を聞いている |
| **正規化** | 正しい声調に丸めた ＝ 漢字からの辞書引き。声調フィードバックは実装不能 |
| **判定不能** | 対象の音節を取り出せなかった、または第三の声調 |
| **誤検出** | 対照群（崩していない）なのに違う声調を報告した |

漢字がどう返ってきたかも独立した手がかりとして表示する。理想は
**「漢字は正しい字（水果）に戻しつつ、ピンインは実音（shuì）で返す」**で、
これが成立するなら声調フィードバックが作れる。

### セット構成（10ケース × 5セット）

| セット | 内容 |
|---|---|
| 1 | 3声 → 4声（日本人学習者に最も多い崩れ方） |
| 2 | 4声 → 2声 |
| 3 | 1声 → 4声 |
| 4 | 2声 → 4声 |
| 5 | 対照群。セット1〜4から10文を選び、崩さずに読ませる。誤検出の測定用 |

ケースごとに ▶ ボタン、セットごとに「このセット10件を実行」、全体で「全50ケースを実行」。
合成した音声はメモリにキャッシュされるので、同じケースを再実行してもTTSは呼び直さない。

### 結果の読み方

画面上部に自動で結論が出る。

- **検出率 ≥ 70% かつ 誤検出 ≤ 20%** → 実装GOの目安
- **検出率 ≤ 10%** → 音を聞かず辞書引きしている。実装しても無意味
- その中間 → グレー。セット別の内訳を見て、特定の声調ペアに絞る等の判断

### 重要な但し書き

この結果は**上限値**として読むこと。

- TTSの声調はきれいに発音されるので、実際の学習者の曖昧な発音より**検出しやすい**。
  **ここで検出できないなら、人の発話では絶対に検出できない**（強い反証になる）。
  逆に検出できても、人の発話で通用するかは別途 `index.html` で確認が要る。
- 置換後の文は意味的に壊れている（「睡果」＝寝る果物）ので、モデルが正しい声調へ
  戻そうとする圧力は最大にかかる。その意味では一番厳しい条件。
- 検出も正規化も起きない場合、**TTSがそもそも崩れた声調を出せていない**可能性がある。
  各ケースの音声プレイヤーで実際に鳴っている音を数件聴いて確かめること。
  漢字が崩れた字（睡）で返ってきていれば、音は崩れていた証拠になる。

### 設定

`gemini-3.1-flash-tts-preview` / 声 `Kore` を初期値にしている。TTSモデル名や声を変えたら
「音声キャッシュを破棄」を押すこと。TTSが404やエラーを返す場合はモデル名を確認する。

## 録音版（index.html）で何を検証するか

**知りたいのは1点だけ。わざと声調を間違えたとき、モデルはその間違いを報告するか？**

LLMのASRは音ではなく語彙として復号するため、ピンインを要求しても
「漢字に確定 → 辞書引き」した結果を返している可能性が高い。もしそうなら
出力は常に正解の声調になり、声調エラーは構造的に検出できない
（＝2出力にしても差分が永遠にゼロ）。それを実測で切り分ける。

### 手順（30分）※録音版

1. HSK3の短文を5つ選ぶ（`assets/data/zh/sentences_3.json` から。ただし現在は
   `claude/chinese-language-support-7hfonn` ブランチ側にある）。
2. 各文につき2テイク録音する:
   - **(a) 正しい声調**で読む
   - **(b) 1音節だけわざと声調を崩す**（例: `我想问你一件事情` の `wèn` → `wén`）
   計10テイク。
3. 「この録音で言おうとした文」に元の漢字を入れる（比較の基準が安定する）。
   「メモ」に (a)/(b) と崩した箇所を書いておく。
4. 各テイクを実行し、結果カードで判定ボタンを押す:
   - **検出できた** … (b) で崩した音節が「声調ちがい」として出た
   - **見逃した** … (b) なのに差分なし、または別の場所だけ出た
   - **誤検出** … (a) なのに声調ちがいが出た
5. 「実験ログをJSONで書き出す」で結果を保存。

### 判定基準

| 結果 | 意味 |
|---|---|
| (b)10本中**7本以上で検出**、かつ (a) の**誤検出2本以下** | そのモードは実用可能。実装GO |
| (b) でも (a) でも**常に差分なし** | 音を聞かずに辞書引きしている。**実装しても無意味**。次のモードへ |
| 検出はするが場所がバラバラ／(a)でも頻繁に出る | もっともらしい嘘。学習アプリとしては何も言わないより有害 |

3モードすべてダメなら、Gemini単体での声調フィードバックは諦めて、
発音評価専用API（SpeechSuper / Chivox 等）を検討するしかない。

## 3つのモード

| モード | 内容 | 狙い |
|---|---|---|
| **案A** ピンイン先出し | 1コールで `{pinyin, hanzi}` をこの順に生成 | 構造化出力は左から順に生成されるので、ピンインを先に出させれば漢字に確定してからの辞書引きを避けられる（かもしれない）。`propertyOrdering` で順序を固定 |
| **案A'** 漢字先出し | 同じコールで `{hanzi, pinyin}` に順序反転 | **対照実験**。案Aと結果が変わらなければ順序は効いていない＝ピンインは常に辞書引き、の証拠 |
| **案B** 2コール | ピンイン専用コール＋漢字コールを分離 | 漢字の文脈に引きずられる経路を物理的に断つ。音声を2回送るぶんコスト増 |

どのモードでも、プロンプトで「学習者の発話である／正しい声調に直すな／ピッチだけを根拠にしろ」を
明示し、模範解答はモデルに渡していない（渡すと確実にそれに引っ張られるため）。

## 「本来あるべき声調」の出し方

漢字（入力した文、無ければ認識結果）を**音声なしのテキストのみのコール**でGeminiに渡し、
標準ピンインを変調適用済みで返させている。音声を渡さないので、聞こえた音が
混入しない＝比較の基準として独立している。

本実装ではここを Dart の `pinyin` / `lpinyin` パッケージによるローカル辞書引きに
置き換えられる（決定的・無料・オフライン）。ただし変調（3声連続・`一`・`不`）と
多音字（`行 xíng/háng` など）の扱いが必要。POCではそこをGeminiに任せている。

## 差分の見方

- **声調ちがい**（黄色）… 音節は同じで声調だけ違う。**これが検出したい本命**
- **別の音節 / 言えていない / 余分**（赤）… そもそも違う語を言った、または認識ずれ。
  この行では声調の判定は当てにならない

音節の対応付けは、声調を無視した素の音節でLCSを取ってから声調差を分離している
（アプリ本体の `lib/utils/word_diff.dart` と同じ考え方）。

## コスト表示

`DESIGN.md` の導入価格（入力 $0.75 / 出力 $3.75 per 1M tokens）で計算。
思考トークンは出力単価。音声は約32トークン/秒。

## 注意

- 音声は16kHzモノラルWAVに変換して送る（アプリ本体の `pcm_converter.dart` と同じ形式）
- 音節分割は貪欲マッチの簡易実装。`fangan` のような切れ目が曖昧な綴りは
  正しく割れないことがある（実用上はモデルが音節をスペース区切りで返すので問題になりにくい）
- これは検証用の使い捨てで、アプリに載せるコードではない
